# 2026-08-22 — repo scaffolded

Build only. No design decisions were made about the queue itself; the sketch starts next.

Code: `build.sbt`, `project/plugins.sbt`, `src/main/protobuf/homelab/keyedqueue/v1/scaffold.proto`
Spec: `src/test/scala/homelab/keyedqueue/ScaffoldSpec.scala` (3 tests, green)

## What exists

An sbt build with ZIO 2.1.23, `homelab-common` + `homelab-postgres` at `0.0.1-alpha` (Magnum, Hikari,
Flyway, postgresql arrive transitively), ScalaPB + zio-grpc codegen, `grpc-netty` as the server transport,
Testcontainers-postgres in `Test`, scalafmt, and the toolkit's strict scalac flags.

Three scaffold tests assert nothing interesting on purpose. They prove the *build* is whole: the toolkit
resolves from GitHub Packages, the generated gRPC types are on the classpath, and zio-test runs. Each is a
separate way the scaffolding could be silently broken. They are listed in the README as files to delete.

## The toolkit is consumable — verified cold

`homelab-toolkit-zio` `v0.0.1-alpha` was released the same day, so this repo doubled as the proof that the
publishing loop works. With the Coursier cache entry for the registry deleted and no `0.0.1-alpha` in
`~/.ivy2/local`, `sbt clean update` pulled both jars over the network and the suite ran green. The published
`homelab-common` jar carries 253 classes (`PollConsumer`, `KeyedQueue`, `Distributer` among them) and an
`Apache-2.0` block in its POM.

Consuming it needs a classic PAT with `read:packages` in `~/.sbt/1.0/credentials` — GitHub Packages serves
Maven only to authenticated callers, public repo or not.

## Two build gotchas, both cost real time

- **ScalaPB generator options must live in the `.proto`, not `build.sbt`.** `scalapb.gen(flatPackage = true)`
  reconfigures ScalaPB alone; zio-grpc's generator reads options from the file. Setting it build-side
  desynchronises them — the ZIO stub kept referring to `…v1.scaffold.PingRequest` after ScalaPB had moved to
  `…v1.PingRequest`, for 26 compile errors inside generated code. Fixed with
  `option (scalapb.options) = { flat_package: true }`.
- **Testcontainers' `getDockerImageName` resolves through the Docker client**, so it needs a running daemon
  even when no container is started. A scaffold test that merely wanted to prove the dependency was present
  failed on a machine without Docker up. It now checks the class is on the classpath instead.

`grpc-netty` is pinned to `scalapb.compiler.Version.grpcJavaVersion` rather than a literal, so the transport
cannot drift from the version the generated code was built against.
